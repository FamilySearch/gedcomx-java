# GedcomX Release Procedure

> **Before your first release:** complete the [Setup](#setup) section below. You cannot
> release GedcomX until it is done.

## Release Lines

We currently maintain two release lines for `gedcomx-java`:

| Release line | Branch   | For projects using          |
|--------------|----------|-----------------------------|
| `4.x.x`      | `master` | Jackson 3 / Spring Boot 4+  |
| `3.x.x`      | `v3.x.x` | Jackson 2 / Spring Boot 3   |

The `2.x.x` release line (branch `v2.x.x`) is **no longer maintained or published.**

To pull and track the `v3.x.x` branch locally:

```bash
git checkout -b v3.x.x origin/v3.x.x
git branch --set-upstream-to=origin/v3.x.x v3.x.x   # may not be necessary
```

## Overview

1. Check your changes into `master`, build it, and release it using the
   [release steps](#release-steps).
2. Switch to the `v3.x.x` branch:

   ```bash
   git checkout v3.x.x
   ```

3. Cherry-pick the desired change(s) made since the last release from `master`:

   ```bash
   git cherry-pick <commitId>
   ```

4. Build and release the `v3.x.x` branch using the [release steps](#release-steps).

## Release Steps

### 1. Verify the build

Make sure the project builds and that all of your changes are checked in.

> ⚠️ **Use Java 17.** Both the `3.x.x` and `4.x.x` release lines are built with Java 17.

### 2. Run the release

```bash
mvn -B -Prelease clean release:clean release:prepare \
    -Dtag=$THIS_RELEASE_VERSION \
    -DreleaseVersion=$THIS_RELEASE_VERSION \
    -DdevelopmentVersion=$NEXT_SNAPSHOT_VERSION \
    -DpushChanges=false -DlocalCheckout=true \
    release:perform
```

Example:

```bash
export THIS_RELEASE_VERSION=3.59.0; \
export NEXT_SNAPSHOT_VERSION=3.60.0-SNAPSHOT; \
mvn -B -Prelease clean release:clean release:prepare -Dtag=$THIS_RELEASE_VERSION -DreleaseVersion=$THIS_RELEASE_VERSION -DdevelopmentVersion=$NEXT_SNAPSHOT_VERSION -DpushChanges=false -DlocalCheckout=true release:perform;
```

What the arguments mean:

| Argument | Meaning |
|----------|---------|
| `-B` | Run in non-interactive (batch) mode. The Release Plugin takes its required parameters from system properties set on the command line, or from the `release.properties` file created by `release:prepare`. |
| `-Prelease` | Activate the `release` profile. (Takes a comma-delimited list of profiles.) |
| `clean` | Clean the files and directories generated by Maven during the build. |
| `release:clean` | Clean up after a release preparation, ensuring a clean project to release. |
| `release:prepare` | Prepare a release in SCM. Requires a Maven project, executes as an aggregator plugin, and creates `release.properties`. |
| `-Dtag=$THIS_RELEASE_VERSION` | The SCM tag to use. |
| `-DreleaseVersion=$THIS_RELEASE_VERSION` | The version to use when preparing the release. |
| `-DdevelopmentVersion=$NEXT_SNAPSHOT_VERSION` | The version to set on the local working copy after the release. |
| `-DpushChanges=false -DlocalCheckout=true` | Don't push to GitHub; the changes are pushed manually after the release. |
| `release:perform` | Perform the release from SCM: check out from the SCM URL and run the predefined Maven goals (`deploy site-deploy`) to release the project. |

To preview what a release would change without actually releasing:

```bash
mvn release:prepare -DdryRun=true
mvn release:clean                  # clean up afterwards
```

### 3. Merge the release changes

Create a PR with the local changes from the release and merge it to `master`.

## After the Release

Once the release finishes you will have artifacts with the new version in your local
repository, but that does **not** mean they have been published to Maven Central. You may
delete them from your local `.m2` repository if you wish.

If the release succeeded, your components were published to Maven Central. They could
appear there within 10 minutes, probably within 2 hours, but it may take longer; updates to
`search.maven.org` can take longer still. Check here:

- https://central.sonatype.com/search?q=gedcomx
- https://repo1.maven.org/maven2/org/gedcomx/

Until the artifacts are on Maven Central, anything trying to use those versions — including
FamilySearch build servers — will fail.

If you try to use an artifact before it is available on Maven Central, expect to wait an
additional 15 minutes before it shows up in the FamilySearch Artifactory repository, which
caches negative lookups for about 15 minutes (or at least Nexus did) before retrying Maven
Central. `mvn -U ...` may work around this.

# Setup

Required before releasing the project.

## 1. Set up an account to publish to the Central Repository

You need a Sonatype account for the Central Repository.

1. **Create an account.** Follow the instructions at
   https://central.sonatype.org/register/central-portal/. Any email address works, but
   using `name@familysearch.org` may make things easier.

2. **Get your Sonatype username added as a member of the `org.gedcomx` group.**
   We haven't had to do this since OSSRH was retired; we'll figure out the current process
   the next time we need to add a user.

3. **Add your Sonatype user token to your local Maven `settings.xml`.** Follow
   https://central.sonatype.org/publish/generate-portal-token/ to generate a user token,
   then copy the generated settings into the `<servers>` section of your Maven
   `settings.xml`, changing `${server}` to `ossrh`. The result should look something like
   this:

   ```xml
   ...
   <servers>
     <server>
       <id>ossrh</id>
       <username>aHxB6UYz</username>
       <password>x+zKbntg+XvbBqTuCPJuJEnq54vlGt/Fs1ohY2ABqQb3k</password>
     </server>
   </servers>
   ...
   ```

## 2. Obtain and export the PGP secret key

The key is used to sign the jar files.

```bash
export PGP_SECRET_KEYFILE=~/.ssh/gedcomx/gedcomx-pgp-key.asc
```

## Accessing Repositories

The repositories below let you access components in OSSRH directly. Users get components
via the Central Repository, but this list can be useful for committers and other
collaborators.

**General public repository group at Sonatype** (contains both snapshots and releases):

- https://oss.sonatype.org/content/groups/public/org/gedcomx

**Staged/released artifacts at Sonatype.** This repository is synced to Maven Central; look
here to verify the project was successfully staged/released at Sonatype (see the notes
below):

- https://oss.sonatype.org/content/repositories/releases/
- https://oss.sonatype.org/content/repositories/releases/org/gedcomx

**Maven Central.** Once the artifacts are here, FamilySearch's Artifactory can pull them:

- https://search.maven.org/search?q=gedcomx
- https://repo1.maven.org/maven2/org/gedcomx
- https://repo.maven.apache.org/maven2/org/gedcomx

**FamilySearch Artifactory** (requires VPN):

- https://familysearch.jfrog.io/ui/packages/gav:%2F%2Forg.gedcomx:gedcomx-model?name=gedcomx-model&type=packages

## Notes on Sync Timing

- Once Central Sync is activated, future promotions are synced automatically. The sync
  process runs roughly every 2 hours.
  ([reference](https://stackoverflow.com/questions/23235892/how-long-does-sonatype-staging-take-to-sync-my-artifacts-with-maven-central?rq=1))
- Upon release, your component is published to Central, typically within 10 minutes, though
  updates to search can take up to two hours.
  ([reference](https://central.sonatype.org/pages/ossrh-guide.html#releasing-to-central))
- In practice, expect somewhere between 10 minutes and 2 hours to reach Maven Central.
  Observed times have ranged from about 30 minutes to 2 hours.
